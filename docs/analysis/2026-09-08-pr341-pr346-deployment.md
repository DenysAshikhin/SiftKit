### One-token MTP comparison

On the merged engine and Next model with 410 CPU experts, compared no MTP, dynamic MTP capped at one draft token, and fixed MTP with one draft token. All modes used 12 CPU threads, 32768-token FP16 caches, 4096-token chunks, host n-gram table, `EXL3_LOAD_ARENA=1`, `EXL3_MOE_MEMOPS=0`, and the native allocator. Dynamic draft confidence target: 0.4.

Used upstream `eval/spec_decode.py`'s `measure` function on its three `Coding` prompts with greedy sampling, thinking disabled, and a 512-output-token cap per prompt. Each generator received a separate 64-token warmup. The models were loaded once; the MTP model remained resident during the no-MTP baseline. Speeds are the upstream benchmark's output-token-weighted mean generation rates, excluding prompt processing. These short coding prompts are a different workload from the preceding teacher-forced `perf.py` context sweep; the 32k setting is cache capacity, not prompt length.

| Mode | Generation tok/s | Versus baseline | Draft acceptance |
|---|---:|---:|---:|
| No MTP | 25.56 | 1.00x | — |
| Dynamic MTP, maximum 1 | 30.10 | 1.18x | 91.3% |
| Fixed MTP, draft 1 | 30.65 | 1.20x | 92.7% |

Per-round records verified that neither MTP mode exceeded one draft token. Dynamic used one on all 803 measured rounds (zero zero-draft rounds); fixed used one on all 797 rounds. Thus dynamic did not shorten any measured window on this workload. The 1.8% fixed-over-dynamic speed difference is too small to establish a robust winner from one pass.

The benchmark changed no saved preset settings. JSON results, draft traces and the benchmark log are archived with the other evidence under `pristine_exle/runs/20260908-pr341-pr346/mtp-*`.

| Prefill chunk size | PP tok/s at 32768 prompt tokens |
|---|---:|
| 1024 | 604.29 |
| 2048 | 1048.39 |
| 4096 (existing result) | 1742.35 |
| 8192 | 2561.78 |

8192 was fastest in this sweep, 47.0% above 4096. These are single-run measurements at 32k, not validation of 8192-token chunks with the saved 155k preset. No preset chunk size was changed.

Prefill chunk size controls prompt-processing work and memory requirements; it does not directly choose the number of tokens verified in a decode step. Decode generally remains similar with unchanged model placement and draft settings, but VRAM pressure or placement changes can affect it indirectly. Decode was intentionally not rerun for this sweep.

### 4k versus 8k VRAM probe

Separate loads with the same 32k FP16 cache, 410 CPU experts, 12 threads, host n-gram table and MTP off. Recorded post-load memory after CUDA synchronization, reset PyTorch peak counters, and ran one complete 32768-token prefill in the selected chunk size. Both probes exited successfully and unloaded the model.

| Metric | 4096 chunks | 8192 chunks | 8k minus 4k |
|---|---:|---:|---:|
| Device-wide VRAM used after load | 20.152 GiB | 20.349 GiB | +202 MiB |
| PyTorch live allocation after load | 18.428 GiB | 18.388 GiB | −40.875 MiB |
| PyTorch reserved after load | 18.557 GiB | 18.754 GiB | +202 MiB |
| Peak live allocation during prefill | 19.897 GiB | 21.083 GiB | +1214.125 MiB |
| Peak reservation during prefill | 20.117 GiB | 21.420 GiB | +1334 MiB |

Device-wide used memory includes the desktop, CUDA context and other allocations; the pre-load device-used baseline was identical in both probes (1601699840 bytes). PyTorch allocation/reservation counters exclude allocations outside that allocator, so they are not total-device peaks. The important additional headroom is approximately 1.19 GiB of live tensors, or 1.30 GiB of allocator reservation, during prefill. Post-load live allocations were nearly unchanged; idle device usage alone would miss the peak difference.

Raw records: `vram-4096.json`, `vram-8192.json` and corresponding logs in the evidence directory.

### Disk-backed n-gram table: 4k and 8k

Ran full `perf.py` PP/decode measurements at chunk sizes 4096 and 8192 with `-ngr` omitted and `EXL3_NGRAM_STREAM=1` explicit. The log records `NGRAM_RAM_REQUESTED False`. All other settings match the 410-expert RAM benchmarks: merged engine, Next model, 12 worker threads, 32768-token FP16 cache, MTP off, native allocator, `EXL3_LOAD_ARENA=1`, `EXL3_MOE_MEMOPS=0`. Both runs completed successfully.

`-ngr`/`--ngram_ram` is opt-in. Without it, `config.infer_params.ngram_stream_from_disk` defaults true. The Windows native gather path opens its streaming handles with `FILE_FLAG_OVERLAPPED | FILE_FLAG_NO_BUFFERING`, bypassing the Windows file cache; drive/controller caches were not controlled.
